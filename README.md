# SPbPU Thesis PDF Checker

Программное средство предназначено для предварительной проверки PDF-файлов выпускных квалификационных работ на соответствие основным требованиям шаблона СПбПУ. Проект использует собственный модуль разбора PDF: из документа извлекаются страницы, текстовые блоки, координаты, размеры шрифтов и метаданные, после чего формируется нормализованная модель документа и применяется каталог правил оформления.

## Назначение

Средство не заменяет экспертный нормоконтроль. Его задача состоит в автоматизированном выявлении формальных признаков, которые могут быть проверены по PDF-файлу до ручной проверки документа. Такой подход позволяет заранее обнаружить типовые нарушения и подготовить структурированный отчёт для последующего анализа.

Проверяются следующие группы признаков:

- наличие обязательных структурных элементов ВКР;
- наличие реферата, ключевых слов и оглавления;
- параметры страницы A4;
- приближённая оценка полей, основного кегля и межстрочного интервала;
- подписи таблиц и рисунков;
- наличие списка источников и внутритекстовых ссылок;
- заполненность служебных метаданных PDF;
- размер PDF-файла.

Для каждого правила в отчёте сохраняются статус, категория, степень значимости, достоверность автоматической оценки, номер страницы и подтверждающий фрагмент текста, если он может быть извлечён из документа.

## Архитектура

Обработка документа выполняется как последовательность этапов:

1. Чтение PDF-файла и выбор стратегии разбора.
2. Извлечение страниц, текстовых блоков, координат и метаданных.
3. Нормализация данных в промежуточную модель ВКР.
4. Применение каталога правил к нормализованной модели.
5. Формирование машинно-читаемого отчёта в формате JSON.

В проекте используются три стратегии разбора PDF:

- `xref` — чтение объектов через таблицу перекрёстных ссылок;
- `stream` — последовательный поиск объектов в потоке байтов;
- `auto` — сначала используется `xref`, при ошибке выполняется резервный переход к `stream`.

Стратегия `auto` применяется в основных сценариях проверки, так как сочетает извлечение метаданных при корректной структуре PDF и устойчивость к повреждённой служебной структуре файла.

## Установка

Требуется Python 3.10 или более новая версия. Рекомендуется использовать изолированное окружение.

```bash
git clone https://github.com/topkaamur/pdf_parser_nir.git
cd pdf_parser_nir
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Для проверки установки можно выполнить команду:

```bash
python -m src.thesis_checker.cli --help
```

## Проверка одного PDF-файла

PDF-файл выпускной квалификационной работы предварительно получают по ссылке электронного ресурса электронной библиотеки СПбПУ (см. раздел «Экспериментальный корпус»). Одиночная проверка выполняется командой:

```bash
python -m src.thesis_checker.cli check /путь/к/документу.pdf \
  --strategy auto \
  --output data/output/report.json
```

Для вывода полного отчёта в стандартный поток используется флаг `--json`:

```bash
python -m src.thesis_checker.cli check /путь/к/документу.pdf --json
```

Код завершения равен `0`, если критические нарушения не обнаружены, и `1`, если отчёт содержит критические замечания. Предупреждения и признаки, требующие ручного анализа, не используются как самостоятельное основание для неуспешного завершения проверки.

## Пакетная проверка корпуса

Пакетная проверка каталога, содержащего PDF-файлы, полученные из электронной библиотеки, выполняется командой:

```bash
python -m src.thesis_checker.cli baseline /путь/к/каталогу \
  --strategy auto \
  --output-dir baseline_reports
```

Команда формирует отдельный JSON-отчёт для каждого PDF-файла и сводный файл `summary.json`. Пример агрегированных результатов приведён в каталоге `baseline_reports`; количественные показатели эксперимента — в [`reports/experiment_report.md`](reports/experiment_report.md).

Опубликованный отчёт по эксперименту находится в [`reports/experiment_report.md`](reports/experiment_report.md). В нём приведены:

- состав корпуса ВКР;
- общая сводка по статусам правил;
- результаты по каждому документу;
- разбивка замечаний по отдельным правилам;
- среднее время проверки по 25 запускам;
- 95 % доверительные интервалы;
- выборочная дисперсия времени обработки.

## Формат JSON-отчёта

JSON-отчёт содержит следующие основные поля:

- `source_file` — путь к проверяемому PDF-файлу;
- `strategy` — фактически применённая стратегия разбора;
- `passed` — отсутствие критических замечаний;
- `summary` — агрегированная сводка по статусам правил;
- `results` — список результатов отдельных правил;
- `document` — сведения о версии PDF, метаданных, количестве страниц и размере файла.

Каждый элемент `results` содержит идентификатор правила, название, категорию, статус, серьёзность, достоверность, пояснение, номер страницы и подтверждающий фрагмент. Пример выходного файла приведён в [`data/output/sample_thesis_report.json`](data/output/sample_thesis_report.json).

## Программный интерфейс

Проверка документа может быть запущена из Python-кода:

```python
from src.thesis_checker.engine import check_pdf_path

report = check_pdf_path("/путь/к/документу.pdf", strategy="auto")
print(report.passed)
print(report.summary())
```

Низкоуровневый модуль разбора PDF также доступен отдельно:

```python
from src import parse_pdf

with open("/путь/к/документу.pdf", "rb") as file:
    document = parse_pdf(file.read(), strategy="auto")

print(document.num_pages)
print(document.metadata)
```

## Тестирование

Автоматизированное тестирование выполняется командой:

```bash
pytest
```

Для получения сведений о покрытии кода используется команда:

```bash
pytest --cov=src --cov-report=term-missing
```

Система тестов включает модульные проверки компонентов разбора PDF, интеграционные проверки полного пути от входного файла до отчёта, регрессионные проверки исправленных ошибок и проверки прикладных правил ВКР.

## Ограничения метода

Проверка основана только на информации, извлекаемой из PDF-файла. Поэтому часть признаков оценивается приближённо: поля определяются по координатам текстовых блоков, межстрочный интервал — по расстояниям между строками, а некоторые структурные элементы могут требовать ручного подтверждения. В таких случаях результат получает статус ручного анализа, а не трактуется как безусловное нарушение.
